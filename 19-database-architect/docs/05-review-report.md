# 05. 통합 리뷰

2026-09-29에 요구사항, 데이터 모델, ERD, 마이그레이션, 테스트, 성능 및 보안 문서의 일관성을 검토했다.

## 1. 최종 판정

| 구분 | 판정 | 근거 |
|---|---|---|
| 학습 과제 | 완료 | 7개 테이블 설계, 적용·롤백 SQL, 제약조건 및 권한 테스트, 성능 비교와 보안 검토를 완료함 |
| 스키마 무결성 | 통과 | `ALL SCHEMA TESTS PASSED` 재확인 |
| 최소 권한 | 통과 | `ALL SECURITY PRIVILEGE TESTS PASSED` 재확인 |
| 성능 검증 | 통과 | 핵심 조회 2개를 10만 건에서 비교하고 100만 건으로 추가 검증함 |
| 실서비스 출시 | 불가 | 애플리케이션 규칙, 개인정보 암호화, 감사, 자동 파기와 백업이 아직 구현되지 않음 |

이번 저장소는 Database Architect 학습 결과물로는 완료됐지만, 운영 가능한 쇼핑몰 전체 시스템은 아니다.

## 2. 요구사항 추적

| 요구사항 | 구현 위치 | 검증 | 결과 |
|---|---|---|---|
| 이메일, 거래 식별자와 주문 항목 리뷰의 유일성 | `001_initial_up.sql`의 UNIQUE 제약조건 | 중복 입력 거부 테스트 | 충족 |
| 금액·수량·평점·상태의 허용 범위 | CHECK 제약조건 | 정상 및 위반 입력 테스트 | 충족 |
| 회원 탈퇴 후 주문 유지 | `orders.user_id ON DELETE SET NULL` | 사용자 삭제 테스트 | 충족 |
| 주문 당시 상품명과 가격 보존 | `order_items` 스냅샷 컬럼 | 상품 변경 후 스냅샷 테스트 | 충족 |
| 주문당 성공 결제 최대 1개 | 부분 UNIQUE 인덱스 | 두 번째 성공 결제 거부 테스트 | 충족 |
| 거래 데이터의 임의 삭제 방지 | FK `ON DELETE RESTRICT`, `shop_app` 권한 제한 | 삭제 및 권한 테스트 | 충족 |
| 법정 보존정보 분리 | `legal_retention_records`, `shop_retention` 역할 | 일반 역할 접근 차단 테스트 | 구조 충족, 자동 파기는 미구현 |
| 사용자 최근 주문 조회 | `(user_id, created_at DESC)` 인덱스 | 10만·100만 건 실행 계획 비교 | 충족 |
| 판매 중인 최신 상품 조회 | ACTIVE 부분 인덱스 | 10만 건 실행 계획 비교 | 충족 |
| 적용 및 롤백 제공 | `001`, `002`, `003`의 up/down SQL | 적용·롤백·재적용 | 충족 |

문서의 논리 모델, ERD와 `001_initial_up.sql`에 정의된 7개 테이블 및 관계가 서로 일치한다. 성능 인덱스와 보안 역할은 초기 스키마에서 분리된 후속 마이그레이션으로 관리한다.

## 3. 필수 수정 — 실서비스 전

현재 학습 범위에서 추가로 고쳐야 할 스키마 오류는 발견되지 않았다. 다만 다음 항목은 실서비스 출시를 막는 필수 작업이다.

### 애플리케이션 트랜잭션 규칙

DB의 단일 행 제약조건만으로 보장할 수 없는 다음 규칙을 서비스 코드와 통합 테스트로 구현해야 한다.

- 주문과 하나 이상의 주문 항목을 원자적으로 생성
- 주문 총액과 주문 항목 합계 일치
- 성공 결제 금액과 주문 총액 일치
- 재고 확인·차감의 동시성 제어
- 허용된 주문 상태 전환만 수행
- 완료된 주문의 실제 구매자만 리뷰 작성
- 법정 보존정보 분리와 회원 삭제를 하나의 실패 처리 단위로 수행

### 개인정보와 감사

- `users.email`, `users.name`을 KMS 기반 AEAD 암호화 구조로 전환
- 이메일 조회와 중복 검사를 위한 keyed HMAC 도입
- 개인정보 및 권한 작업을 위한 수정 불가능한 감사 로그 구현
- 파라미터 바인딩과 동적 정렬 허용 목록을 애플리케이션 코드에서 검증

### 데이터 수명주기와 복구

- `retention_until`이 지난 법정 보존정보의 정기 파기 작업 및 실행 감사 구현
- 불필요해진 외부 거래 식별자의 삭제 또는 비식별 처리 정책 구현
- 암호화 백업, 보존기간, RPO/RTO와 복원 훈련 절차 수립

## 4. 개선 권장

다음은 현재 결과를 무효화하지 않지만 요구가 커지면 측정 후 추가할 항목이다.

- 상품별 리뷰 목록을 위한 `order_items(product_id, order_id)` 계열 인덱스 검토
- 주문 상세의 전체 결제 시도 조회를 위한 `payments(order_id, created_at)` 인덱스 검토
- 기간별 주문 집계를 위한 상태·시각 인덱스 또는 집계 테이블 검토
- 상품 가격순 조회가 실제 핵심 기능이면 별도의 ACTIVE 부분 인덱스 비교
- 페이지가 깊어질 경우 OFFSET 대신 마지막 `(created_at, id)`를 이용한 키셋 페이지네이션 적용
- 입출고 이력과 예약 재고가 필요할 때 재고 원장으로 분리
- 상태 변경 감사가 필요할 때 주문·결제 상태 이력 테이블 추가
- CI에서 빈 DB 생성부터 마이그레이션, 테스트와 롤백을 자동 실행

인덱스는 예상만으로 추가하지 않고 실제 쿼리, 데이터 분포, 쓰기 비용과 실행 계획을 함께 측정한다.

## 5. 적용 및 롤백 순서

빈 학습용 DB의 적용 순서는 다음과 같다.

1. `001_initial_up.sql`
2. `seeds/sample-data.sql` 및 `schema-tests.sql` — 검증 환경에서만 실행
3. `002_performance_indexes_up.sql`
4. `003_security_roles_up.sql`
5. `security-tests.sql`

전체 롤백은 의존 관계의 역순인 `003_security_roles_down.sql` → `002_performance_indexes_down.sql` → `001_initial_down.sql`로 실행한다. `001_initial_down.sql`은 모든 학습 데이터를 삭제하므로 로컬 전용이며 운영 롤백 절차로 사용할 수 없다.

## 6. 확인 완료

- [v] 요구사항의 모든 미결정 사항이 모델 문서에서 결정됨
- [v] 모델 문서, ERD와 초기 마이그레이션의 엔티티·관계가 일치함
- [v] 모든 FK에 UPDATE 및 DELETE 정책이 명시됨
- [v] 마이그레이션마다 적용 및 롤백 SQL이 존재함
- [v] 제약조건의 정상·실패 사례와 사용자 삭제 정책을 테스트함
- [v] 최종 인덱스가 실제 실행 계획, 버퍼, 시간과 크기를 기준으로 선택됨
- [v] 최소 권한 역할과 법정 보존정보 접근 격리를 테스트함

## 7. 회고

### 배운 점

- 좋은 데이터 모델은 테이블 목록보다 업무 규칙, 삭제 정책과 데이터 수명주기에서 시작한다.
- 모든 규칙을 DB 제약조건으로 해결할 수 없으므로 DB와 애플리케이션의 책임 경계를 명시해야 한다.
- 인덱스는 존재 여부가 아니라 실행 계획, 정렬 제거, 버퍼, 데이터 분포와 쓰기 비용으로 평가해야 한다.
- 회원 탈퇴는 사용자 행을 계속 보관하는 문제가 아니라 필요한 거래 기록과 개인정보를 분리하는 문제다.
- 보안 검토 완료와 실서비스 보안 구현 완료는 서로 다른 상태다.

### 잘된 점

- 요구사항에서 SQL, 테스트, 성능 측정과 권한 설계까지 결정 근거가 이어진다.
- 마이그레이션과 테스트를 반복 실행해 적용뿐 아니라 롤백 가능성도 확인했다.
- 10만 건 균등 데이터에 머물지 않고 편향 분포와 100만 건 확장 검증을 수행했다.
- 해결하지 못한 운영 위험을 숨기지 않고 후속 작업으로 기록했다.

### 다음에 개선할 점

- 애플리케이션을 연결해 트랜잭션 규칙과 SQL Injection 방어를 통합 테스트한다.
- 동시 결제와 재고 차감을 여러 세션에서 시험한다.
- 백업을 실제로 복원하고 목표 복구 시간과 데이터 손실 범위를 측정한다.
- 운영과 유사한 동시 읽기·쓰기 부하에서 인덱스의 전체 비용을 다시 평가한다.
