# 00. 요구사항과 액세스 패턴

## 1. 프로젝트 범위

작은 쇼핑몰의 주문 과정을 지원하는 PostgreSQL 데이터베이스를 설계한다.

이번 실습에 포함하는 기능:

- 사용자 가입 및 조회
- 상품 등록, 가격 및 재고 상태 관리
- 주문 생성과 주문 항목 저장
- 결제 시도와 결과 기록
- 구매한 상품에 대한 리뷰 작성

이번 실습에서 제외하는 기능:

- 장바구니와 쿠폰
- 배송 추적
- 판매자 정산
- 추천 시스템
- 실제 결제사 연동

범위를 벗어난 기능은 필요성이 생기더라도 바로 구현하지 않고 `미결정 사항`에 기록한다.

## 2. 핵심 엔티티

| 엔티티 | 책임 | 대표 데이터 |
|---|---|---|
| 사용자(User) | 구매자 계정 관리 | 이메일, 이름, 상태 |
| 상품(Product) | 판매 가능한 상품 관리 | 이름, 현재 가격, 판매 상태 |
| 주문(Order) | 한 번의 구매 행위 관리 | 주문자, 상태, 총액, 주문 시각 |
| 주문 항목(Order Item) | 주문에 포함된 상품과 주문 당시 조건 보존 | 상품, 수량, 주문 당시 단가 |
| 결제(Payment) | 주문에 대한 결제 시도와 결과 기록 | 결제 수단, 금액, 상태, 거래 식별자 |
| 리뷰(Review) | 구매자의 상품 평가 관리 | 작성자, 상품, 평점, 내용 |

## 3. 업무 규칙

### 사용자

- 이메일은 필수이며 사용자 간 중복될 수 없다.
- 탈퇴한 사용자의 개인정보 처리 방식은 별도로 결정해야 한다.
- 과거 주문의 정합성을 위해 사용자를 즉시 물리 삭제하지 않는다.

### 상품

- 상품 가격은 0 이상이어야 한다.
- 판매 중단된 상품도 과거 주문에서 확인할 수 있어야 한다.
- 상품의 현재 가격이 바뀌어도 과거 주문 금액은 바뀌면 안 된다.

### 주문과 주문 항목

- 하나의 주문에는 하나 이상의 주문 항목이 있어야 한다.
- 주문 항목의 수량은 1 이상이어야 한다.
- 주문 항목에는 주문 당시 상품명과 단가를 보존한다.
- 주문 총액은 주문 항목 금액의 합과 일치해야 한다.
- 주문 상태는 허용된 상태 사이에서만 전환되어야 한다.

초기 주문 상태 후보:

```text
PENDING -> PAID -> PREPARING -> SHIPPED -> COMPLETED
    |        |
    +--------+-> CANCELLED
```

상태 전환을 DB 제약조건만으로 보장할지 애플리케이션과 함께 보장할지는 이후 단계에서 결정한다.

### 결제

- 한 주문에 여러 결제 시도가 존재할 수 있다.
- 성공한 결제의 금액은 주문 총액과 일치해야 한다.
- 외부 결제 거래 식별자는 중복될 수 없다.
- 카드 번호, CVC 같은 원본 결제정보는 저장하지 않는다.

### 리뷰

- 평점은 1점부터 5점까지다.
- 사용자는 실제 구매한 상품에만 리뷰를 작성할 수 있다.
- 동일한 주문 항목에 리뷰는 하나만 작성할 수 있다.
- 리뷰 작성 가능 시점은 주문 완료 이후로 제한한다.

## 4. 주요 액세스 패턴

인덱스는 컬럼 목록이 아니라 아래 조회 패턴을 기준으로 설계한다.

| 우선순위 | 사용 사례 | 조건과 정렬 | 예상 빈도 |
|---:|---|---|---|
| 1 | 사용자의 최근 주문 목록 | `user_id`, `created_at DESC`, 페이지네이션 | 높음 |
| 2 | 주문 상세 조회 | `order_id`와 주문 항목, 결제 | 높음 |
| 3 | 판매 중인 상품 목록 | 판매 상태, 최신순 또는 가격순 | 높음 |
| 4 | 상품 리뷰 목록 | `product_id`, `created_at DESC` | 중간 |
| 5 | 결제 거래 조회 | 외부 거래 식별자 | 중간 |
| 6 | 기간별 주문 집계 | 주문 상태와 주문 시각 범위 | 낮음/배치 |

다음 단계에서 각 패턴에 대응하는 SQL을 먼저 작성한 뒤 인덱스를 결정한다.

## 5. 예상 규모와 가정

- 사용자: 최대 100만 명
- 상품: 최대 10만 개
- 주문: 하루 최대 10만 건
- 주문당 항목: 평균 3개, 최대 50개
- 결제 시도: 주문당 평균 1회, 최대 5회
- 리뷰: 완료된 주문 항목의 약 10%
- 기준 시간대: DB에는 UTC로 저장하고 표시할 때 변환
- 기준 DBMS: PostgreSQL 16

위 수치는 실제 측정값이 아닌 학습을 위한 가정이다. 성능 문서에서 이 가정을 명시하고 검증 가능한 범위만 결론을 내린다.

## 6. 비기능 요구사항

- 금액은 부동소수점 타입을 사용하지 않는다.
- 모든 주요 테이블에 생성 시각을 기록한다.
- 변경 시각이 필요하다면 갱신 책임이 DB와 애플리케이션 중 어디에 있는지 명시한다.
- 모든 FK에 삭제 및 갱신 정책을 명시적으로 지정한다.
- 스키마 변경은 적용 및 롤백 스크립트를 함께 제공한다.
- 애플리케이션 DB 계정에는 최소 권한만 부여한다.
- 개인정보와 외부 거래 식별자가 로그에 무분별하게 출력되지 않도록 한다.

## 7. 미결정 사항

다음 질문은 데이터 모델링 단계에서 결정하고 근거를 남긴다.

- 사용자 탈퇴 시 개인정보를 익명화할 것인가, 별도 보관 후 삭제할 것인가?
- 재고 수량을 이 실습의 스키마가 직접 관리할 것인가?
- 주문 총액을 저장할 것인가, 주문 항목에서 매번 계산할 것인가?
- 상품명 스냅샷을 주문 항목에 저장할 것인가?
- 주문 상태 변경 이력 테이블을 별도로 둘 것인가?
- 결제 성공을 부분 고유 인덱스로 제한할 것인가?
- 대량 주문 데이터를 언제 파티셔닝할 것인가?
