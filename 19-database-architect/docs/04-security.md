# 04. 보안 검토

이 문서는 쇼핑몰 데이터베이스를 최소 권한, 개인정보, 법정 보존, 감사와 복구 관점에서 검토한 결과다. 로컬 실습에서 확인 가능한 역할과 권한은 `003_security_roles` 마이그레이션으로 구현하고, 애플리케이션·KMS·운영 인프라가 필요한 항목은 후속 조치로 구분한다.

## 1. 보호 대상 데이터

| 데이터 | 위치 | 민감도 | 처리 원칙 |
|---|---|---|---|
| 이메일, 이름 | `users` | 높음 | 서비스 목적 동안만 처리하고 탈퇴 시 파기 |
| 사용자와 주문 연결 | `orders.user_id` | 중간 | 탈퇴 시 `ON DELETE SET NULL`로 연결 제거 |
| 결제 거래 식별자 | `payments.transaction_id` | 중간 | 카드 원문 대신 외부 거래 식별자만 저장 |
| 법정 보존 개인정보 | `legal_retention_records.retained_data_encrypted` | 매우 높음 | 애플리케이션 암호화, 접근 역할 분리, 만료 후 파기 |
| 리뷰 내용 | `reviews.content` | 중간 | 불필요한 개인정보 입력 방지와 신고·삭제 정책 필요 |
| 비밀번호, 카드번호, CVC | 저장하지 않음 | 매우 높음 | 인증 제공자와 결제사업자에 위임하고 DB 저장 금지 |

가명처리된 식별자나 해시도 다른 정보와 결합해 개인을 알아볼 수 있으면 보호 대상에서 제외하지 않는다.

## 2. 역할과 최소 권한

모든 역할은 `NOLOGIN` 그룹 역할로 만든다. 실제 운영 로그인 역할은 배포 환경에서 별도로 생성하고 필요한 그룹 역할만 부여한다. 비밀번호나 인증서는 저장소에 커밋하지 않는다.

| 역할 | 목적 | 주요 권한 |
|---|---|---|
| `shop_owner` | 객체 소유 | 테이블과 함수 소유, 직접 로그인 불가 |
| `shop_migrator` | 승인된 스키마 변경 | `shop_owner` 역할 전환, 스키마 CREATE |
| `shop_app` | 일반 서비스 | 업무 테이블의 제한된 DML, DDL 및 법정 보존정보 접근 불가 |
| `shop_retention` | 법정 보존 처리 | 주문 조회, 법정 보존 레코드 입력·조회·파기 |
| `shop_readonly` | 분석과 지원 | 일반 업무 테이블 SELECT, 쓰기 및 법정 보존정보 접근 불가 |

`PUBLIC`에는 `shop_lab` 접속·임시 객체 생성 및 `public` 스키마 사용 권한을 주지 않는다. 모든 역할의 `search_path`는 `pg_catalog, public`으로 고정해 신뢰하지 않는 스키마의 객체가 먼저 해석되는 위험을 줄인다.

`shop_app`의 삭제 권한은 다음과 같이 제한한다.

- `users`: 탈퇴 처리에 필요하므로 DELETE 허용
- `reviews`: 서비스 정책에 따른 삭제를 위해 DELETE 허용
- `products`, `orders`, `order_items`, `payments`: 거래 보존을 위해 DELETE 금지

## 3. 개인정보 암호화 계획

현재 `users.email`과 `users.name`은 평문이므로 실제 운영 전 개선이 필요한 높은 위험 항목이다. 애플리케이션과 키 관리 시스템이 없는 이번 DB 실습에서는 스키마를 임의로 암호화하지 않고 다음 후속 설계를 기록한다.

권장 구조:

```text
email_ciphertext        AEAD 방식으로 암호화한 이메일
email_lookup_hash       정규화된 이메일의 keyed HMAC
name_ciphertext         AEAD 방식으로 암호화한 이름
encryption_key_version  키 교체를 위한 버전
```

- 단순 SHA 해시 대신 서버 측 비밀키를 사용하는 HMAC으로 이메일 중복과 조회 키를 만든다.
- 암호화에는 인증된 암호화 방식(AEAD)을 사용한다.
- 암호화 키는 DB와 환경 파일이 아니라 KMS 또는 비밀 관리 시스템에 저장한다.
- 키 교체 시 이전 버전 데이터를 점진적으로 재암호화한다.
- 로그, 오류 메시지와 분석 데이터에는 평문 이메일을 남기지 않는다.

`legal_retention_records.retained_data_encrypted`는 DB가 암호화 여부를 판별할 수 없으므로 애플리케이션 경계에서 암호화되지 않은 입력을 거부해야 한다.

## 4. SQL Injection 방어

DB 권한만으로 SQL Injection을 막을 수 없으므로 애플리케이션에서 다음을 강제한다.

- 값은 문자열 연결 없이 prepared statement와 파라미터 바인딩으로 전달한다.
- 테이블명, 정렬 컬럼과 방향처럼 바인딩할 수 없는 값은 서버의 허용 목록으로 변환한다.
- `shop_app`에는 DDL, 역할 관리, 스키마 생성과 법정 보존정보 접근 권한을 부여하지 않는다.
- 오류 응답에 SQL, 스키마명, 개인정보와 연결 문자열을 노출하지 않는다.
- DB 드라이버에서 다중 SQL 문 실행을 기본적으로 허용하지 않는다.

## 5. 법정 보존과 자동 파기

탈퇴 처리 시 필요한 최소 정보만 애플리케이션에서 암호화해 법정 보존 테이블로 이동한 뒤 `users` 행을 삭제한다.

정기 작업은 최소 하루 한 번 다음 조건의 행을 삭제해야 한다.

```sql
DELETE FROM legal_retention_records
WHERE retention_until <= CURRENT_TIMESTAMP;
```

파기 작업은 `shop_retention` 권한으로 실행하고 실행 시각, 파기 범주, 삭제 건수, 작업 ID와 성공·실패 결과를 감사 기록에 남긴다. 개인정보 원문이나 암호문 자체는 감사 로그에 남기지 않는다.

## 6. 감사 로그 계획

다음 이벤트는 애플리케이션의 append-only 감사 저장소에 기록한다.

- 개인정보 조회·변경·삭제
- 법정 보존정보 생성·조회·파기
- 결제 상태 변경
- 역할과 권한 변경
- 마이그레이션 실행
- 인증 실패 및 비정상적인 대량 조회

권장 필드:

```text
event_id, occurred_at, actor_id, actor_role, action,
resource_type, resource_id, request_id, source_ip,
result, reason
```

감사 로그 작성 실패 시 민감 작업을 계속할지 중단할지 이벤트별 정책을 정해야 한다. 일반 애플리케이션 역할은 감사 로그를 수정하거나 삭제할 수 없어야 한다. 이번 실습에는 애플리케이션이 없으므로 감사 저장소 구현은 후속 과제로 남긴다.

## 7. 백업과 복구

운영 환경에서는 다음이 필요하다.

- 백업 파일과 전송 구간 암호화
- 운영 DB와 다른 자격증명을 사용하는 백업 역할
- 백업 저장소 접근 권한과 보존기간 제한
- 개인정보 파기 정책에 백업 데이터의 만료와 복원 후 재파기 절차 포함
- 정기 복원 훈련으로 RPO와 RTO 검증
- 백업 성공 알림뿐 아니라 실제 복원 가능성 확인

로컬 Docker 볼륨은 백업 전략이 아니며 삭제하거나 손상되면 복구를 보장하지 않는다.

## 8. Row-Level Security 판단

이번 모델은 하나의 쇼핑몰을 위한 단일 테넌트 구조이므로 RLS를 적용하지 않는다. 판매자나 조직별로 동일 테이블을 공유하는 멀티테넌트 구조로 변경되면 모든 업무 테이블에 `tenant_id`를 추가한 뒤 RLS 정책과 우회 권한을 별도로 검토한다.

## 9. 발견 사항

| 심각도 | 발견 사항 | 상태 | 조치 |
|---|---|---|---|
| 높음 | 이메일과 이름이 평문으로 저장됨 | 미해결 | KMS 연동 후 암호문 + keyed HMAC 구조로 마이그레이션 |
| 높음 | 개인정보 및 권한 작업의 불변 감사 로그가 없음 | 미해결 | 애플리케이션 감사 저장소 설계·구현 |
| 중간 | 법정 보존 만료 데이터의 자동 파기 작업이 없음 | 미해결 | `shop_retention` 정기 작업과 실행 감사 추가 |
| 중간 | 백업·복원 및 백업 내 개인정보 파기 절차가 없음 | 미해결 | 운영 환경의 암호화 백업과 복원 훈련 설계 |
| 중간 | 애플리케이션의 파라미터 바인딩을 검증할 코드가 없음 | 확인 필요 | 애플리케이션 구현 시 코드 리뷰와 통합 테스트 |
| 낮음 | 역할 분리 없이 소유자 계정을 사용할 위험 | 해결 | `003_security_roles`로 NOLOGIN 그룹 역할과 최소 권한 적용 |
| 낮음 | 일반 역할이 법정 보존정보에 접근할 위험 | 해결 | `shop_retention` 전용 권한으로 분리 |
| 정보 | 카드번호와 CVC 저장 가능성 | 충족 | 스키마에 원본 결제정보 컬럼을 만들지 않음 |

미해결 항목은 현재 학습 범위를 벗어났다는 뜻이지 운영 출시가 가능하다는 뜻이 아니다. 실제 서비스 배포 전에는 모두 담당자, 기한과 검증 기준이 있는 작업으로 전환해야 한다.

## 10. 검증 체크리스트

- [v] 소유자, 마이그레이션, 애플리케이션, 보존, 읽기 역할을 분리함
- [v] 모든 그룹 역할을 `NOLOGIN`으로 구성함
- [v] 일반 애플리케이션의 DDL 권한을 제거함
- [v] 법정 보존정보 접근을 전용 역할로 제한함
- [v] 거래 테이블의 물리 삭제 권한을 제한함
- [v] 개인정보 항목과 보유·파기 경계를 식별함
- [v] 원본 결제정보를 저장하지 않음을 확인함
- [v] SQL Injection 방어 경계를 정의함
- [v] 감사 대상 이벤트와 필드를 정의함
- [v] 백업·복구 및 백업 개인정보 처리 요구사항을 정의함
- [v] RLS 미적용 근거와 재검토 조건을 기록함

## 11. 실행 결과

2026-09-29에 PostgreSQL 16 학습 환경에서 다음 순서로 검증했다.

1. `003_security_roles_up.sql` 적용
2. `security-tests.sql` 실행
3. `003_security_roles_down.sql` 적용
4. 다섯 역할 제거 및 일곱 테이블의 `lab` 소유권 복원 확인
5. `003_security_roles_up.sql` 재적용
6. `security-tests.sql` 재실행

두 차례의 권한 검사 모두 `ALL SECURITY PRIVILEGE TESTS PASSED`를 출력했다. 최종 데이터베이스에는 보안 역할 마이그레이션이 적용되어 있다.
