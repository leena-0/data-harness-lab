# 04. 모니터링과 운영

## 테스트 원칙

6단계 테스트는 실제 사이트에 요청하지 않는다. 저장된 HTML fixture와 Scrapy의 가짜 응답을 사용하며, 재시도 대기 함수도 mock으로 교체하여 테스트가 실제로 기다리지 않게 한다.

`unittest` 테스트 범위는 다음과 같다.

- 목록에서 상세 페이지와 다음 페이지 요청 생성
- 외부 도메인 링크 제외
- 상품 목록, 페이지 번호 또는 다음 링크가 사라진 구조 변경 감지
- 401, 403, 429 접근 거부 시 중단 정책
- 상세 요청 실패는 격리하고 목록 요청 실패는 중단하는 정책
- 서버 오류와 네트워크 예외 재시도
- 지수 백오프, 최대 대기 시간과 `Retry-After` 처리
- 저장 커밋 이후의 통계 증가
- 파싱 성공률 품질 검사와 JSON 요약 생성

## 재시도 정책

재시도 대상과 횟수는 `settings.py`에서 관리한다. 재시도 간격은 기본 1초에서 시작해 `1, 2, 4, ...`초로 증가하며 최대 60초를 넘지 않는다. 서버가 `Retry-After`를 전달하면 지수 백오프와 비교해 더 긴 시간을 적용한다.

재시도 횟수를 모두 사용한 뒤에는 다음과 같이 처리한다.

- 개별 상세 페이지 실패: 통계와 로그를 남기고 다른 상품을 계속 수집한다.
- 목록 페이지 실패: 이후 페이지를 신뢰할 수 없으므로 크롤링을 중단한다.
- 접근 거부: 우회하지 않고 즉시 중단한다.

## 수집 통계

`books/` 접두사가 붙은 다음 통계를 수집한다.

| 통계 | 의미 |
| --- | --- |
| `listing_pages_seen` | 처리한 목록 페이지 수 |
| `detail_requests_scheduled` | 생성한 상세 요청 수 |
| `detail_pages_seen` | 응답을 받은 상세 페이지 수 |
| `detail_items_parsed` | 검증을 통과한 상품 수 |
| `detail_parse_failures` | 검증에 실패한 상품 수 |
| `detail_request_failures` | 재시도 후 실패한 상세 요청 수 |
| `listing_request_failures` | 재시도 후 실패한 목록 요청 수 |
| `retry_count` | 수행한 재시도 수 |
| `offsite_links_skipped` | 제외한 외부 또는 잘못된 링크 수 |
| `db_items_stored` | SQLite 커밋이 완료된 아이템 수 |

`db_items_stored`는 SQL 실행 직후가 아니라 트랜잭션 커밋이 성공한 뒤 증가한다. 따라서 롤백된 아이템은 성공 통계에 포함되지 않는다.

## 품질 검사

파싱 성공률은 다음 식으로 계산한다.

```text
파싱 성공 수 / (파싱 성공 수 + 파싱 검증 실패 수)
```

기본 최소 성공률은 95%다. 처리한 상세 페이지가 없거나 성공률이 95%보다 낮으면 `books/quality_gate_failed`를 `1`로 기록하고 `ERROR` 로그를 남긴다. 품질 검사는 결과를 숨기지 않기 위한 표시이며, 개별 상품 하나의 실패만으로 크롤링을 즉시 중단하지는 않는다.

## 실행 결과

크롤링이 끝나면 `data/processed/crawl-stats.json`에 다음 내용을 저장한다.

- 시작 및 종료 시각
- 종료 사유
- 품질 검사 결과와 실패 이유
- 주요 수집 통계

JSON은 임시 파일을 완성한 뒤 최종 파일로 원자적으로 교체한다. 생성 결과는 Git에 포함하지 않으며, 실제 전체 크롤링과 결과 검토는 7단계에서 수행한다.

## 로그 수준

- `INFO`: 정상 진행, 재시도와 최종 요약
- `WARNING`: 개별 상품 또는 링크 문제
- `ERROR`: 구조 변경, 접근 거부, 저장 오류와 품질 검사 실패

테스트 실행 명령은 다음과 같다.

```bash
cd 37-web-scraper
source .venv/bin/activate
python -m unittest discover -s tests -v
```
